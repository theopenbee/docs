---
title: 聊天指令
description: 在 IM 聊天中通过斜杠指令快速、确定地触发操作
---

除了使用自然语言（例如"清除会话"）之外，OpenBee 还支持一组可以直接在 IM 聊天中输入的斜杠指令。斜杠指令由系统直接解析，不经过 AI 引擎，所以**即刻执行、不消耗 token，行为完全确定**。

当你想要快速、可预期的结果时，用斜杠指令；自然语言的方式依然可用，但它要经过 Bee 的理解和判断。

## 概览

| 指令 | 作用 |
|------|------|
| `/engine` | 切换 Bee 或指定数字员工所用的 AI 引擎 |
| `/clear` | 清除当前聊天的会话上下文，可选只清理某一个数字员工 |
| `/stop` | 停止当前聊天中正在运行的 Bee，并取消队列中尚未处理的消息 |

所有指令在所有支持的 IM 平台（飞书、钉钉、企业微信、Telegram、微信以及本地聊天）上都能使用。它们必须是消息的**第一个词**——像"帮我执行 `/clear`"这样的表达会被当作普通消息发给 Bee，不会触发指令。

## `/engine`

切换正在使用的 AI 引擎。OpenBee 内置 4 个引擎：`claude`、`codex`、`pi`、`kimi`。只有在 `config.yaml` 中启用的引擎可以被选中，详见 [配置](/docs/guide/configuration)。

### 语法

```text
/engine                           # 显示用法提示
/engine {engine}                  # 切换默认引擎（Bee 以及所有未单独绑定引擎的数字员工都会随之切换）
/engine {engine} {workerName}     # 仅切换指定数字员工的引擎
```

| 参数 | 是否必填 | 说明 |
|------|----------|------|
| `engine` | 除纯 `/engine` 外必填 | 引擎名称，必须是当前服务端已启用的引擎 |
| `workerName` | 选填 | 要绑定的数字员工。省略时修改的是系统默认引擎 |

### 示例

切换整个部署的默认引擎：

```text
/engine claude
```

响应：

```text
已将默认 engine 切换为 claude
```

把某个数字员工单独切到另一个引擎：

```text
/engine codex DocBot
```

响应：

```text
已将 Worker "DocBot" 的 engine 切换为 codex
```

查看用法：

```text
/engine
```

响应：

```text
用法：
/engine {engine} — 切换默认 engine
/engine {engine} {workerName} — 切换指定 worker 的 engine
```

### 工作机制

- **默认切换** (`/engine {engine}`)：更新系统配置中的 `default_engine` 字段并刷新内存缓存。Bee 以及所有**没有单独绑定引擎**的数字员工会在下一次运行时使用新引擎。
- **数字员工级切换** (`/engine {engine} {workerName}`)：只修改该数字员工记录的 `engine` 字段，不影响默认引擎，也不影响其他数字员工。

未绑定引擎的数字员工会自动跟随当前默认引擎；一旦给某个数字员工单独设置了引擎，就会以员工级配置为准，不再跟随默认引擎变化。

### 繁忙状态保护

在有任务进行中时切换引擎，会让执行流和会话上下文处于不一致的状态。因此 `/engine` 在下列任一情况下会**拒绝**切换，并告诉你是哪种情况拦住了它：

| 拦截原因 | 提示信息 |
|----------|----------|
| 平台消息正在接收或处理中 | `当前有消息正在接收或处理中，无法切换引擎，请等待完成后再试。` |
| 至少有一个 execution 正在运行 | `当前有执行中的 execution，无法切换引擎，请等待完成后再试。` |
| 至少有一个即时任务待处理或运行中 | `当前有即时任务正在等待或执行中，无法切换引擎，请等待完成后再试。` |

三项检查并行执行；优先级依次是消息、执行、任务。等被指出的活动结束后再重试。

### 错误响应

| 场景 | 提示信息 |
|------|----------|
| 引擎名未在服务端启用 | `未知的 engine: {name}，支持的 engine：claude / codex / pi / kimi` |
| 找不到该数字员工 | `Worker "{name}" 不存在` |
| 数据库写入失败 | `切换失败，请稍后重试` |

### 什么时候用 `/engine`

- 更换了 API 密钥或调整了预算，想整体切到另一个服务商。
- 某个数字员工承载较重，想单独让它跑在更便宜或更快的引擎上，其他保持不变。
- 想先在单个数字员工上试用新引擎，再决定是否推到整个部署。

## `/clear`

清理当前 IM 聊天累积的会话上下文。会话由"聊天 + 用户"标识，因此 `/clear` 只影响你发送指令所在的这个聊天。

### 语法

```text
/clear                      # 清除本会话所有代理（Bee + 数字员工）的上下文
/clear {workerName}         # 只清除本会话中指定数字员工的上下文
```

| 参数 | 是否必填 | 说明 |
|------|----------|------|
| `workerName` | 选填 | 要清理的数字员工。省略时会清除本会话所有代理的上下文 |

### 示例：清除单个数字员工

```text
/clear DocBot
```

响应：

```text
✅ 已清除 DocBot（engine：claude）的会话上下文。
```

只移除 DocBot 的对话上下文。Bee 的上下文、其他数字员工的上下文以及正在进行的任务都不受影响。

### 示例：清除整个会话

没有运行中任务时，清理立即执行：

```text
/clear
```

响应：

```text
✅ 已清除：Bee (claude), DocBot (claude)
```

如果会导致运行中任务被取消，`/clear` 会先要求二次确认：

```text
/clear
```

响应：

```text
⚠️ 将清除以下会话上下文：Bee (claude), DocBot (claude)
同时将终止 2 个运行中任务。
30s 内再发一次 /clear 确认。
```

在 30 秒内再次发送 `/clear` 即执行清理；超时后确认失效，下一次 `/clear` 会重新开始这个流程。

确认后：

```text
✅ 已清除：Bee (claude), DocBot (claude)，取消了 2 个任务。
```

### 具体清了什么

整体清理 (`/clear`)：

1. 停止本会话中所有正在进行的 execution。
2. 取消本会话中所有待处理和运行中的即时任务。
3. 删除 Bee 以及所有在本会话中有活跃上下文的数字员工的对话上下文。

员工级清理 (`/clear {workerName}`)：

1. 只删除该数字员工在其当前引擎上的对话上下文。
2. **不会**停止 execution，也**不会**取消任务。

两种形式都不会动数字员工的记忆、数字员工配置，也不会影响其他聊天的上下文。

<BeeNote>
  `/clear` 只清**当前聊天**的会话上下文，不会影响你在其他群或私聊里的对话记忆，也不会删掉数字员工的持久记忆 — 清得干净但不误伤 🐝
</BeeNote>

### 错误与边界响应

| 场景 | 提示信息 |
|------|----------|
| 本聊天没有任何代理的上下文 | `没有可清除的会话` |
| 找不到该数字员工 | `Worker "{name}" 不存在` |
| 有多个同名数字员工 | `存在多个同名 Worker "{name}"：` 后面列出每个数字员工的名称和 UUID |
| 确认超时（未取消任何任务） | 下一次 `/clear` 重新进入确认流程，没有额外报错 |

如果指定的数字员工存在但在当前会话里没有活跃上下文（比如它从没在此聊天被调用过），也会回 `没有可清除的会话`。

### 什么时候用 `/clear`

- **切换话题**：主动清一次再切换，可以避免旧上下文串到新对话里。
- **重置单个出状况的数字员工**：优先用 `/clear {workerName}`，不动 Bee 和其他数字员工。
- **快速止损**：整体 `/clear` 一步到位停掉所有 execution；30 秒确认的设计就是为了防止误操作。
- **精简膨胀的上下文**：当响应变慢或数字员工引用过时信息时，清一下是最快的恢复方式。

## `/stop`

立即停止当前聊天中正在运行的 Bee，并取消队列中尚未处理的待发消息。该指令只作用于你发送它所在的聊天会话，不影响其他会话。

### 语法

```text
/stop     # 停止当前会话中正在运行的 Bee，并取消待处理消息
```

`/stop` 不接受任何参数。

### 响应

系统根据执行指令时的实际状态返回不同的提示：

| 情况 | 提示信息 |
|------|----------|
| Bee 正在运行，无待处理消息 | `✅ 已停止 bee 执行` |
| Bee 正在运行，有待处理消息 | `✅ 已停止 bee 执行，取消了 N 条待处理消息` |
| Bee 未运行，有待处理消息 | `✅ 已取消 N 条待处理消息` |
| 无任何需要停止的内容 | `当前会话没有需要停止的内容` |

### 工作机制

发送 `/stop` 后，系统依次执行两步操作：

1. **取消 Bee 执行** — 若 Bee 正在运行，系统会立即取消其 Go context。取消信号会沿执行链路向下传播，Bee 在遇到下一个感知 context 取消的检查点时停止，不会等待当前轮次执行完毕。
2. **清理待处理消息** — 所有处于 `received`（已接收、待处理）状态的消息会被标记为 `failed`，防止 Bee 在停止后自动继续处理这些消息。

`/stop` **不会**清除会话上下文、停止 Worker 执行，也不会取消计划任务。如需这些操作，请使用 `/clear`。

### 什么时候用 `/stop`

- **中断耗时过长的回复**：Bee 响应太慢或答非所问 — 发一条 `/stop` 立即打断。
- **撤回刚发出的消息**：消息发出后还没被 Bee 处理，改变主意了 — `/stop` 可以从队列中清除它。
- **解除卡住的 Bee**：Bee 看起来没有反应、停滞不动 — `/stop` 强制终止执行。
- **执行完整重置前的准备**：先用 `/stop` 排空进行中的任务，再用 `/clear` 清除上下文，两步组合实现彻底重置。

### 注意事项

- **幂等性** — 在没有任何运行内容时调用 `/stop` 是安全的，会返回"当前会话没有需要停止的内容"，不产生任何副作用。
- **会话作用域** — 只影响你发送 `/stop` 所在的聊天，其他会话不受影响。
- **消息记录保留** — 被停止的消息在数据库中被标记为 `failed`，不会被删除。
- **无需二次确认** — 与有运行任务时的 `/clear` 不同，`/stop` 立即执行，不需要确认步骤。

## 斜杠指令 vs. 自然对话

你也可以用普通聊天消息来表达同样的意图（例如"清除会话"、"把引擎切到 codex"）。两种方式都能用，但取舍不一样：

| | 斜杠指令 | 自然对话 |
|---|----------|----------|
| **速度** | 立即执行，不调用 AI | 较慢，需要 Bee 解读 |
| **成本** | 免费，不消耗 token | 消耗 Bee 的 token |
| **确定性** | 输入确定 → 结果确定 | 取决于 Bee 的理解 |
| **表达力** | 语法固定 | 可接受近似说法、同义词、多步意图 |
| **撤销** | 无撤销；只有破坏性 `/clear` 有确认 | Bee 对歧义的说法会主动追问 |

当你**非常明确**想做什么并且希望立刻生效时，用斜杠指令；当意图比较开放（比如"重置刚才那个一直报错的数字员工"）时，用自然对话更合适。

## 最佳实践

### 把 `/clear` 当成日常维护指令

把 `/clear` 当成"刷缓存"一样使用 — 切换话题、开始重要新任务之前，或者发现代理行为跑偏时都可以用。员工级 `/clear` 便宜且不破坏性，不用等整个会话坏掉才想起它。

### 用 `/engine` 前先确认引擎可用

只有服务端配置里启用的引擎才能被选中。如果 `/engine {name}` 返回 `未知的 engine`，说明这个引擎还没装或没配置 — 去 `config.yaml` 里修好，不要反复重试指令。

### 别在高峰时段跑 `/engine`

繁忙状态检查会拒绝切换，但反复尝试只会刷屏。最好在空闲时段统一切换引擎，或者先暂停消息再切。

### 优先用员工级 `/clear`，少用整体 `/clear`

整体 `/clear` 会取消正在运行的任务并抹掉 Bee 的协调历史。除非这正是你想要的，否则优先 `/clear {workerName}` — 精准清理，保留会话其他部分的状态。

### 用 `/stop` + `/clear` 实现彻底重置

`/stop` 负责排空进行中的任务，`/clear` 负责清除上下文。需要彻底重置时 — 没有运行中的 Bee、没有待处理消息、没有历史上下文 — 按顺序执行：先 `/stop`，看到确认后再 `/clear`。
